# Causal Attribution in Renewal Churn

Companion code for the article **"When Customers Churn at Renewal: Was It the Price or the Project?"** ([Towards Data Science](https://medium.com/towards-data-science) — *link to be added once published*).

The notebook reproduces every figure and numerical result in the article on a synthetic B2B SaaS dataset where the true causal effects are known, so you can verify each method recovers them.

## What the notebook does

A single end-to-end pipeline that runs three different causal methods on the same data:

1. **Difference-in-Differences** with a triple interaction `post * A * B`
2. **Regression with interaction terms** at the customer level
3. **Shapley value attribution** of the joint churn impact

Plus an LTV breakeven analysis that translates the recovered churn effect into a pricing recommendation.

## What you should see

The simulation has these true effects baked in:

| Cohort                              | True 6-month churn |
|-------------------------------------|--------------------|
| Neither force                       | 8%                 |
| Promo expiry only                   | 13%                |
| Initiative completion only          | 12%                |
| Both forces (with +5 pp interaction)| 22%                |

Each method recovers these values up to sampling variability:

- **DiD** picks up `post:A`, `post:B`, and the triple interaction `post:A:B` separately
- **Regression** recovers `b1`, `b2`, `b3` close to the simulation truth (0.05, 0.04, 0.05)
- **Shapley** allocates the 14 pp joint impact roughly 7.5 / 6.5 between the two drivers
- **LTV breakeven** lands around $1,324, a 32% increase, not the 13% that shipped

## Notes

- All randomness is seeded (`np.random.default_rng(42)`). Results should be exactly reproducible across runs.
- The DiD section uses HC3 robust standard errors. Cluster-robust standard errors at the cohort level are not a great fit here because there are only four cohorts. With a real customer-segment grouping you would want clustered standard errors and probably a wild cluster bootstrap.
- `initiative_complete` is randomly assigned in this simulation. In production it must be defined using pre-renewal CRM, implementation, or customer success milestones, not from post-hoc usage decline.
